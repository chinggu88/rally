# 커뮤니티 탭 기획서

> 작성일 2026-08-23 · 대상 버전 1.1.0 · 상태: 초안(리뷰 대기)

---

## 1. 배경

Rally는 BWF 배드민턴 팬을 위한 **소비 전용** 앱이다. 라이브 스코어 · 대회 일정 · 세계 랭킹 · 뉴스 매거진 · 관심 선수 푸시 — 전부 "보는" 기능이고, 사용자가 남기는 것은 없다.

유일한 UGC인 `live_match_chat`(경기별 실시간 채팅)은 경기 중에만 살아 있다가 종료와 함께 죽는다. 메시지는 DB에 영구 보존되지만 재유입 동선이 없다.

**결과: 재방문 동기가 BWF 일정에 100% 종속된다.** 투어가 없는 주에는 앱을 열 이유가 없고, 축적되는 콘텐츠가 없으니 검색·공유를 통한 신규 유입도 발생하지 않는다.

### 앱 성격에서 도출한 기회

앱스토어 메타데이터는 타겟을 *"배드민턴 팬"* 으로 잡고 있지만, 실제 한국 사용자 대다수는 **관전자이자 동시에 동호인**이다. 주 2~3회 체육관에서 직접 치고, 라켓·스트링·셔틀콕을 사고, 같이 칠 사람을 구한다. 이 일상 니즈는 **경기 일정과 무관하게 상시 발생**한다.

로그인 화면 카피가 이미 *"프리미엄 배드민턴 커뮤니티"* 라고 선언하고 있으나(`login_view.dart:142`) 실체가 없다. 커뮤니티 탭은 그 약속을 이행하는 동시에, 관전 앱에서 **동호인 앱**으로 외연을 넓히는 전환점이다.

### 목표

| # | 목표 | 측정 |
|---|---|---|
| 1 | 비경기일 리텐션 확보 | BWF 투어 비개최일 DAU (출시 전 대비) |
| 2 | 축적되는 콘텐츠 자산 | 주간 신규 게시글 / 댓글 수 |
| 3 | 로그인 전환 | 커뮤니티 경유 신규 가입 비율 |
| 4 | 체류시간 증가 | 세션당 평균 체류시간, 커뮤니티 탭 점유율 |

현재 로그인은 관심 선수 알림에만 필요해 가입 동기가 약하다. 커뮤니티는 **읽기는 비로그인 허용 / 쓰기는 로그인 필수**로 설계해 자연스러운 전환 퍼널을 만든다.

## 2. 정보 구조

### 2-1. 바텀 네비게이션: 4탭 → 5탭

```
홈(0)  경기(1)  선수(2)  커뮤니티(3)  내정보(4)
```

**커뮤니티를 4번째(내정보 앞)에 배치한다.**

- 기존 사용자의 경기(1)·선수(2) 위치 근육기억을 깨지 않는다. 신규 탭을 중앙에 끼워 넣으면 기존 동선 두 개가 한 칸씩 밀린다.
- 부수 효과로 `AppController`의 `matchTabIndex = 1` / `playerTabIndex = 2` 하드코딩 상수가 그대로 유효하다.
- `app_theme.dart`의 `bottomNavigationBarTheme`에 `type: BottomNavigationBarType.fixed`가 이미 지정돼 있어 5탭에서도 라벨이 유지된다(shifting 전환 없음).

**라벨은 "커뮤니티"로 하고, 바텀 네비 라벨 크기를 14 → 12pt로 낮춘다.** (확정 D-1)

iOS 최소 지원이 13.0이라 320pt 기기(iPhone SE 1세대)가 설치 범위에 들어온다. 5탭이면 아이템당 64pt인데 `AppTypography.labelLg`(14pt, letterSpacing 0.7)로 "커뮤니티" 4글자는 약 59pt라 여유가 거의 없다.

라벨 단어를 타협하는 대신 폰트를 줄인다 — 현재 14pt는 바텀 네비 기준으로 큰 편이고 **Material 표준이 12sp**라, 이 변경은 문제 해결과 정돈을 동시에 얻는다. `app_theme.dart`의 `bottomNavigationBarTheme` 한 줄 수정이며 5개 탭 전체에 적용된다.

"소통"·"게시판" 같은 단축안은 채택하지 않는다 — 로그인 화면 카피가 이미 *"프리미엄 배드민턴 커뮤니티"* 라 브랜드 용어를 일치시키는 편이 낫다.

아이콘: `Icons.forum_outlined` / `Icons.forum` (기존 탭의 outlined/filled 쌍 관례 준수)

### 2-2. 카테고리 5종

| 표시 라벨 | DB 값 | 용도 |
|---|---|---|
| 전체 | *(필터 미적용)* | 기본 진입 화면 |
| 자유 | `free` | 잡담, 관전 감상 |
| 경기토론 | `match` | 특정 경기·선수 관련 토론 |
| 장비 | `gear` | 라켓·스트링·셔틀콕 후기와 질문 |
| 파트너찾기 | `partner` | 같이 칠 사람, 지역 클럽 모집 |

**"파트너찾기"가 이 앱만의 차별점이다.** BWF 관전 앱에는 없는 국내 동호인 고유 니즈이며, 다른 배드민턴 앱 대비 방어 가능한 해자다. 초기 트래픽이 여기서 나올 가능성이 가장 높다.

한국어 라벨은 DB에 넣지 않고 클라이언트 상수로 관리한다 — `PlayerController._categoryLabelsKo` / `_categoryLabelsEn` 패턴을 그대로 따른다.

## 3. 화면 정의

모든 리스트 화면은 프로젝트 정형 패턴인 **로딩 / 에러+재시도 / 빈 상태 / 정상** 4단 분기를 갖는다.

### S-1. 커뮤니티 목록 (`/community`)

```
┌─────────────────────────────┐
│ Rally                       │  AppBar — 라임 워드마크 (기존 탭 공통)
├─────────────────────────────┤
│ [전체][자유][경기토론]        │  가로 스크롤 칩 (44.h)
│ [장비][파트너찾기]           │
├─────────────────────────────┤
│ ┌─────────────────────────┐ │
│ │ 장비 · 스매시왕 · 1시간   │ │  카드: #1C1B1B + #2A2A2A 보더 + 16r
│ │ 아스트록스 100ZZ 후기     │ │  제목 Chivo w700
│ │ 3개월 써본 소감 정리...   │ │  본문 2줄 ellipsis
│ │ [썸네일]  ♥51 💬17 👁240 │ │
│ └─────────────────────────┘ │
└─────────────────────────────┘
                        (＋)     FAB 글쓰기
```

- `RefreshIndicator` + `CustomScrollView`, 무한 스크롤 임계값 300px (`PlayerView` 패턴)
- 정렬: 최신순 고정 (인기순은 범위 밖 — §9-J 참조)
- FAB: `app_theme.dart:86`에 라임 배경 FAB 테마가 이미 정의돼 있으나 앱 전체에서 미사용. **이 화면이 첫 사용처**다.
- 비로그인도 목록·상세를 볼 수 있다. FAB 탭 시 로그인 유도.
- **빈 상태**: 카테고리별 문구 차등. 파트너찾기는 *"첫 파트너 모집 글을 올려보세요"* 처럼 작성을 유도한다.

### S-2. 게시글 상세 (`/community/post`)

- 작성자(아바타·닉네임·시간) / 카테고리 칩 / 제목 / 본문 / 이미지 그리드
- 하단 액션 바: 좋아요 토글, 댓글 수, 조회수
- 댓글 리스트 → 대댓글은 1depth 들여쓰기
- 우상단 더보기(⋯): 본인 글이면 **수정/삭제**, 타인 글이면 **신고/차단**. 운영자면 관리자 액션 추가 노출
- 진입 시 조회수 +1 (1인 1회, §5-4)

### S-3. 글 작성 / 수정 (`/community/compose`)

- 카테고리 선택 칩 → 제목(최대 100자) → 본문(최대 5000자) → 이미지 첨부(최대 5장)
- 이미지는 `image_picker`의 `pickMultiImage(limit: 5)`, `profile_edit_controller` 패턴 준수
- **최초 작성 시 온보딩 시트를 먼저 띄운다** — 닉네임 설정 + 이용규칙 동의 (S-6)
- 금칙어 클라이언트 사전 검증 → 즉시 피드백 (서버가 최종 권위)

### S-4. 신고 시트 (바텀시트)

사유 6종 라디오 + 상세 입력(최대 500자) + 제출.
제출 완료 시트에서 곧바로 **"이 사용자 차단하기"** CTA를 제공한다 — 신고자가 체감하는 처리 시간이 0초가 된다.

| 사유 값 | 라벨 |
|---|---|
| `spam` | 스팸 / 광고 |
| `abuse` | 욕설 / 비방 |
| `sexual` | 음란물 |
| `illegal` | 불법 정보 |
| `privacy` | 개인정보 노출 |
| `other` | 기타 |

### S-5. 차단한 사용자 (`/blocked-users`)

내정보 메뉴 하위. 차단 목록 + 개별 해제. `favorite_players_view.dart`의 리스트 구조를 그대로 따른다.

### S-6. 커뮤니티 시작하기 (바텀시트)

최초 글/댓글 작성 시 1회. **닉네임 설정과 이용규칙 동의를 한 시트에서 함께 받는다.** (확정 D-5)

```
┌─ 커뮤니티 시작하기 ──────┐
│ 닉네임                   │
│ ┌──────────────────┐    │
│ │ 스매시왕          │    │  실시간 중복 검사
│ └──────────────────┘    │
│ ✓ 사용 가능한 닉네임      │
│                          │
│ [이용규칙 본문 스크롤]     │
│                          │
│ ☑ 이용규칙에 동의합니다    │
│ ┌──────────────────┐    │
│ │   동의하고 계속    │    │
│ └──────────────────┘    │
└──────────────────────────┘
```

- 이미 닉네임이 있는 사용자는 닉네임 입력란을 건너뛰고 약관만 받는다
- 이용규칙은 내정보 메뉴에서도 상시 열람 가능해야 한다 (Apple 요구사항)

[커뮤니티 탭 진입]
   │  비로그인도 목록/상세 열람 가능

                    │
                    └─ 로그인됨 ──→ 이용규칙 동의했나?

`User_{uid앞4자리}` 폴백(`chat_message_bubble.dart:182`)은 **커뮤니티에서는 표시되지 않는다** — 작성 전에 닉네임이 반드시 설정되기 때문이다. 다만 라이브 채팅에는 기존 사용자가 남아 있으므로 폴백 로직 자체는 유지한다.

## 5. 기능 상세

### 5-1. 게시글

| 항목 | 규격 |
|---|---|
| 제목 | 1~100자 (공백 제외) |
| 본문 | 1~5000자 |
| 이미지 | 최대 5장, 장당 5MB, jpeg/png/webp/heic |
| 수정 | 본인만, `edited_at` 기록 후 "수정됨" 표시 |
| 삭제 | 소프트 삭제(`status='deleted'`). 물리 삭제 안 함 — 신고 증거 보존 |

### 5-2. 댓글

- 본문 1~1000자, **대댓글은 1depth까지** (대댓글에 답글 불가)
- 삭제된 부모 댓글은 *"삭제된 댓글입니다"* 툼스톤으로 남긴다 — 대댓글이 고아가 되지 않도록 스레드 구조를 유지
- 정렬: 작성순(오름차순)

### 5-3. 좋아요

- 게시글만 (댓글 좋아요는 범위 밖)
- `(post_id, user_id)` 복합 PK로 중복 원천 차단
- 클라이언트 낙관적 업데이트 → 실패 시 롤백
- **"누가 좋아요 눌렀는지" 목록은 제공하지 않는다** — 차단 우회 정보가 되기 때문

### 5-4. 조회수

**로그인 사용자 1인 1회 영구 카운트.**

- 상세 진입 시 `community_increment_view(post_id)` RPC 1회 호출
- 비로그인은 카운트하지 않는다 (과소집계 수용, 라벨은 "조회")
- 클라이언트 로컬 dedup만으로는 재설치 시 무한 증가하므로 서버에서 `community_post_views` 테이블로 판정

### 5-5. 닉네임 (확정 D-2 · D-5)

커뮤니티는 닉네임이 곧 신원이므로 채팅보다 규칙이 엄격하다.

| 항목 | 규격 |
|---|---|
| 필수 여부 | **첫 글/댓글 작성 전 필수** (S-6 온보딩 시트) |
| 길이 | 2~12자 |
| 유니크 | **대소문자·공백 정규화 기준 전역 유일** |
| 금칙어 | 닉네임에도 동일 필터 적용 |
| 변경 | 내정보 → 프로필 편집에서 가능 (중복 검사 추가 필요) |

**유니크 제약을 지금 넣는다.** 현재 프로필 15건 중 닉네임 보유는 4건, 정규화 기준 중복은 1쌍뿐이라 마이그레이션 비용이 사실상 0이다(수동 개명 1건). 사용자가 늘어난 뒤에 추가하면 훨씬 비싸진다.

```sql
alter table public.profiles
  add column if not exists nickname_norm text
  generated always as (lower(btrim(nickname))) stored;

create unique index if not exists profiles_nickname_norm_key
  on public.profiles (nickname_norm)
  where nickname_norm is not null and nickname_norm <> '';
```

- 부분 유니크 인덱스라 **닉네임 미설정(NULL) 사용자 11명은 그대로 공존**한다 — 기존 사용자를 강제 이주시키지 않아도 된다
- 중복 INSERT/UPDATE는 `23505`로 실패하므로, `profile_edit`과 온보딩 시트 양쪽에서 이를 잡아 *"이미 사용 중인 닉네임입니다"* 로 변환한다
- `profile_edit_controller.save()`는 현재 빈 값만 막고 중복은 검사하지 않는다(`profile_edit_controller.dart:80`) — 수정 대상

> 사칭 방지가 목적이다. 게시판에서는 닉네임이 발화의 신뢰도를 결정하므로 채팅보다 위험도가 높다.

## 6. 모더레이션 · 앱스토어 심사 (Apple Guideline 1.2)

UGC를 포함하는 앱은 App Review Guideline 1.2를 충족해야 한다. **이건 선택 기능이 아니라 심사 통과의 전제 조건**이며, 하나라도 빠지면 리젝된다.

| # | Apple 요구사항 | 충족 방법 |
|---|---|---|
| ① | 부적절한 콘텐츠 필터링 | 금칙어 서버 트리거 (posts/comments BEFORE INSERT·UPDATE) |
| ② | 신고 메커니즘 | S-4 신고 시트 (게시글/댓글/사용자) |
| ③ | 악용 사용자 차단 | S-5 차단 기능 (양방향 즉시 차단) |
| ④ | 24시간 내 조치 | §6-3 3중 구조 |
| ⑤ | 이용약관(EULA) 동의 | S-6 동의 시트 + 서버 강제 |
| ⑥ | 개발자 연락처 공개 | 내정보 → 문의 (현재 스텁, §9-C 참조) |

### 6-1. 금칙어 필터

공백·특수문자를 제거한 정규화 문자열로 비교해 `ㅅ ㅂ`, `씨-발` 류 회피를 막는다.
클라이언트가 동일한 정규화 로직으로 사전 검증해 즉시 피드백하고, **서버 트리거가 최종 권위**를 갖는다.

### 6-2. 차단

- 양방향: 내가 차단한 사람의 글도, 나를 차단한 사람의 글도 서로 안 보인다
- **서버(RLS)에서 필터링한다.** 클라이언트 필터링은 페이지네이션에 구멍을 내고(20건 받아 17건 표시), 목록·상세·댓글·알림딥링크 등 모든 경로에서 빠뜨리기 쉬워 리젝 사유가 된다
- 차단 사실은 차단당한 쪽에 노출하지 않는다

### 6-3. 24시간 내 조치 — 3중 구조

Apple이 실제로 확인하는 것은 "사람이 24시간 대기하는가"가 아니라 **"24시간 내 조치할 수 있는 메커니즘이 존재하는가"** 다.

**① 자동 숨김 — 사유별 차등 임계값** (확정 D-4)

| 신고 사유 | 임계값 | 근거 |
|---|---|---|
| `sexual` 음란물 · `illegal` 불법 정보 | **1건** | 고위험. 밤새 방치되면 App Store 리스크이자 실제 피해 |
| `abuse` · `privacy` · `spam` · `other` | **3건** | 담합·오탐 저항 |

일괄 3건으로 잡으면 초기 DAU가 수십 명인 상황에서 서로 다른 신고자 3명이 모이는 일이 거의 없어, 자동 숨김이 사실상 작동하지 않고 24시간 보장이 운영자 푸시 단일 장치에 의존하게 된다.

고위험 사유의 1건 임계값은 악용 소지가 있지만(누구나 남의 글을 "음란물"로 신고해 숨길 수 있다), **자동 숨김은 되돌릴 수 있고 운영자에게 즉시 푸시가 가므로 오탐은 몇 분 단위로 복구된다.** 반대 방향의 실수 — 실제 음란물을 몇 시간 노출 — 은 복구가 불가능하다. 비대칭이 명확하다.

구현은 트리거 안의 `CASE` 한 줄 차이다. 반복 허위 신고자 추적은 2차 범위.

**② 운영자 즉시 푸시** — 신고 1건부터 운영자에게 FCM 푸시.
이 프로젝트에는 이미 `notifications` 테이블 INSERT → DB Webhook → `send-push` Edge Function → FCM 파이프라인이 완성돼 있다. **트리거에서 INSERT 한 줄만 하면 추가 인프라 없이 운영자 폰에 수 초 내 알림이 간다.** 24시간 SLA의 실질적 담보가 이것이다.

**③ 앱 내 관리자 조치** — 운영자 계정으로 로그인하면 기존 더보기 시트에 관리자 항목이 조건부로 추가된다: 숨기기 / 복구 / 삭제 / 작성자 정지 / 신고 종결.
**별도 관리자 화면을 만들지 않는다.** 폰에서 이동 중에도 처리 가능해야 24시간이 지켜진다.

폴백으로 Supabase Studio용 운영 큐 뷰(`community_moderation_queue`)를 두되 `service_role` 전용으로 잠근다.

## 7. 데이터 모델

### 7-1. 접근 방식

**유저 스코프 데이터이므로 Edge Function이 아니라 `.from()` + RLS 직접 접근**을 쓴다.
`chat_message_repository.dart` / `notification_repository.dart` / `favorite_player_repository.dart`가 이미 이 방식이다. `docs/architecture.md`의 *"PostgREST 직접 접근 금지"* 규약은 공개 BWF 데이터(대회·선수·매치·뉴스)에만 적용된다.

### 7-2. 테이블

| 테이블 | 역할 | 핵심 |
|---|---|---|
| `community_posts` | 게시글 | `category` CHECK 4종, `image_paths text[]`(최대 5), 카운터 4종 비정규화, `status` visible/hidden/deleted, `author_id` **nullable + on delete set null** |
| `community_comments` | 댓글·대댓글 | `parent_id` 자기참조 + `(parent_id, post_id) → (id, post_id)` 복합 FK로 타 게시글 부모 지정 차단 |
| `community_post_likes` | 좋아요 | `(post_id, user_id)` PK |
| `community_post_views` | 조회 dedup | `(post_id, user_id)` PK |
| `community_reports` | 신고 | target_type post/comment/user, 신고자별 대상 1회 유니크 |
| `user_blocks` | 차단 | `(blocker_id, blocked_id)` PK, self-block CHECK |
| `user_agreements` | 약관 동의 | `(user_id, doc)` PK + version |
| `community_banned_words` | 금칙어 | `norm` generated column(정규화) + 유니크 |
| `app_admins` | 운영자 | RLS ON + 정책 0개 = 클라 접근 전면 차단 |

기존 `profiles`에 두 가지를 추가한다:
- `community_banned_until timestamptz` — 사용자 정지용
- `nickname_norm` generated column + 부분 유니크 인덱스 (§5-5)

**`author_id`는 `on delete set null`로 둔다** (확정 D-3). posts·comments 모두 해당하며, `auth.users` 삭제 시 글은 남고 작성자만 비워진다. 기존 RLS 정책의 `author_id = auth.uid()` 비교는 NULL일 때 결과가 NULL → false로 평가되므로 안전하다(익명화된 글은 아무도 수정·삭제할 수 없다).

### 7-4. 반드시 지켜야 할 서버 설계 결정 5가지

구현 단계에서 하나라도 빠지면 보안 구멍이거나 조용한 버그가 된다.

**① 컬럼 단위 권한** — Supabase 기본 default privileges가 `public` 신규 테이블에 `GRANT ALL to anon, authenticated`를 자동으로 붙인다. RLS는 행 단위라 컬럼을 막지 못하므로 `like_count = 99999`, `status = 'visible'` 같은 **자기 행 조작을 RLS만으로는 막을 수 없다.**

```sql
revoke all on public.community_posts from anon, authenticated;
grant select on public.community_posts to anon, authenticated;
grant insert on public.community_posts to authenticated;
grant update (title, content, category, image_paths, edited_at)
  on public.community_posts to authenticated;
-- DELETE 권한은 주지 않는다. 소프트 삭제는 RPC로.
```

> **이 결정의 파급효과**: `status` 컬럼에 GRANT 가 없으므로 **운영자도 `.from().update({'status': ...})` 로 글을 숨길 수 없다.** RLS 정책(`is_app_admin()`)은 통과하지만 컬럼 권한에서 42501 로 막힌다 — 정책은 "행"을, GRANT 는 "컬럼"을 통제하며 **둘 다** 통과해야 한다. 정책만 보고 검토하면 놓친다.
> 따라서 관리자의 숨김·복구는 `community_set_post_status()` / `community_set_comment_status()` **definer RPC** 로 처리한다. 삭제·정지·신고종결과 같은 경로라 일관성도 좋다.

**② 헬퍼 함수는 `security definer`** — 양방향 차단 판정은 반드시 함수 경유여야 한다. 정책 안에서 `user_blocks`를 인라인 서브쿼리로 읽으면 `ub_select_own`(blocker_id = me) RLS가 역방향 행을 걸러내 **"나를 차단한 쪽" 필터가 조용히 무력화**된다.

```sql
create or replace function public.community_is_blocked(p_other uuid)
returns boolean language sql stable security definer set search_path = public as $$
  select p_other is not null and auth.uid() is not null and exists (
    select 1 from public.user_blocks b
    where (b.blocker_id = auth.uid() and b.blocked_id = p_other)
       or (b.blocker_id = p_other     and b.blocked_id = auth.uid())
  );
$$;
```

**③ 카운터 트리거도 `security definer`** — 트리거 함수는 호출자 권한으로 실행되므로, 남의 글에 댓글을 달면 posts UPDATE RLS(작성자만)에 막혀 **예외 없이 0건 UPDATE로 조용히 실패**한다. 본인 계정 하나로 테스트하면 절대 재현되지 않는다. **QA는 반드시 계정 2개로.**

**④ 피드 뷰에 `security_invoker = on`** — 작성자 프로필과 `is_liked`를 라운드트립 1회에 얻기 위해 뷰를 만든다. 이때 invoker를 빼면 뷰 소유자(postgres) 권한으로 실행돼 **status 필터와 차단 필터가 전부 우회**되어 삭제·숨김 글까지 노출된다.

> ⚠️ 기존 `public_profiles` view는 **의도적으로** invoker 없이 만들어져 있다(노출 컬럼을 id/nickname/avatar_url 3개로 최소화해 정당화). 그걸 참고해 복붙하면 정반대의 결과가 나온다. 마이그레이션 주석에 이 대비를 반드시 명시한다.

**⑤ Realtime publication에 추가하지 않는다** — `live_match_chat_messages` 선례를 습관적으로 따라 `alter publication supabase_realtime add table`을 하면 안 된다. `replica identity full` 상태에서 `view_count`/`like_count` UPDATE가 매번 본문 5000자를 포함한 전체 행을 WAL과 Realtime으로 흘려보낸다. 댓글 실시간은 MVP 범위 밖이다.

### 7-5. 카운터 전략

**비정규화 컬럼 + 트리거. `count(*)` 금지.**

PostgREST에서 `select('*, community_post_likes(count)')` 형태는 임베드마다 서브쿼리가 붙고, 정렬·필터에 쓸 수 없으며, 중첩 응답이 `MODEL_GUIDE.md`의 flat `fromJson` 컨벤션과 맞지 않는다. 비정규화 컬럼이면 피드가 인덱스 스캔 1회 + 라운드트립 1회로 끝난다.

카운터 컬럼은 **어떤 인덱스에도 포함하지 않고** `fillfactor = 85`를 준다 → HOT UPDATE가 유지되어 인덱스 bloat이 생기지 않는다. (인기순 정렬을 MVP에서 빼는 이유이기도 하다. `like_count` 인덱스를 만드는 순간 HOT이 깨진다.)

정합성 복구용 관리자 함수 `community_recount(post_id)`를 함께 둔다.

### 7-6. 이미지 저장

**신규 `community` 버킷 (public, 5MB 제한).** `avatars`에 섞으면 용량 관리와 정리 정책이 엉킨다.

- 경로: `{user_id}/{draft_id}/{index}_{ts}.jpg`
  `draft_id`는 작성 화면 진입 시 클라이언트가 생성하는 UUID (INSERT 전엔 post_id가 없으므로)
  첫 세그먼트를 `user_id`로 유지해야 기존 `avatars` RLS 패턴을 그대로 재사용할 수 있다
- **DB에는 URL이 아니라 path를 저장한다.** `profiles.avatar_url`은 full URL이지만 여기선 path가 옳다 — 고아 정리 시 `storage.objects.name`과 직접 대조 가능하고, CDN 도메인 변경에 무영향이며, 나중에 private 전환 시 signed URL로 갈아타기가 무료다. 클라이언트가 `getPublicUrl(path)`로 변환
- SELECT 정책은 만들지 않는다 — public 버킷은 `/object/public/`로 읽히고, 광범위 SELECT는 파일 목록 노출 경고를 유발한다. `20260622000200_harden_profiles_security.sql`에서 `avatars_read`를 제거한 것과 동일한 판단

**고아 파일은 "제출 시 업로드"로 원천 차단한다.**
작성 화면에서는 로컬 `File`만 보관하고 프리뷰를 그린다 → "등록" 탭 시 ① 이미지 업로드 → ② 게시글 INSERT → ②가 실패하면 catch에서 방금 올린 path들을 `storage.remove()`. 크론이 필요 없다.
수정 시 이미지 교체는 **업로드 → UPDATE 성공 → 옛 path 제거** 순서. 반대로 하면 실패 시 이미지가 증발한다.

## 9. 리스크

### A. 앱스토어 메타데이터가 "UGC 없음"으로 신고돼 있다 🔴

`appstore_metadata_ko.md`에 *"사용자 생성 콘텐츠(채팅 등)가 이번 버전에 없다면 대부분 4+"* 로 적혀 있고 App Review Notes에도 UGC 언급이 없다.

커뮤니티 출시 시 **연령 등급 재설문 + App Privacy 재신고 + 심사 메모 갱신**이 필요하다. 심사 메모에 §6-3의 24시간 대응 체계를 명시한다.

### B. 기존 라이브 채팅에 신고/차단이 전혀 없다 🔴

`live_match_chat_view.dart`에 신고·차단 관련 코드가 **0건**이다. 즉 앱은 *이미* 모더레이션 없는 UGC를 배포 중이며, 현 상태 그대로 재심사를 받으면 커뮤니티와 무관하게 리젝될 수 있다.

**커뮤니티용으로 만드는 `community_reports` / `user_blocks` 인프라를 라이브 채팅에도 소급 적용한다.** 이건 부수 작업이 아니라 심사 통과의 전제다. 채팅 버블 롱프레스 메뉴에 신고/차단을 추가하고, 차단된 사용자의 메시지를 숨기면 된다 — 테이블은 공용이므로 추가 비용이 작다.

### C. 앱 내 연락 수단이 없다 🟡

Apple 1.2는 개발자 연락처 공개도 요구하는데 `my_info_controller.dart:109-110`의 `goToHelp` / `goToFeedback`이 둘 다 `_showComingSoon` 스텁이다. 최소한 `url_launcher`로 `mailto:` 링크라도 실동작시켜야 한다.

### D. 닉네임에 유니크 제약이 없다 ✅ 해결

`profiles.nickname`은 nullable이고 중복을 허용했다(`profile_repository.dart:47`에 검사 없음). 게시판에서는 사칭 경로가 된다.

**실데이터 확인 결과** — 전체 프로필 15건 중 닉네임 보유 4건, 정규화 기준 중복 1쌍, 미설정 11건. 마이그레이션 비용이 사실상 0이므로 **지금 유니크 제약을 넣는다**. 미설정 11건은 부분 유니크 인덱스로 그대로 공존한다. → §5-5

여기서 파생된 더 큰 발견이 **미설정 11/15**다. 채팅에서는 `User_a3f2` 폴백이 버텼지만 게시판 목록이 이 이름으로 도배되면 앱이 고장 난 것처럼 보이고, 초기 유입자가 글을 쓰지 않는다. **첫 글 작성 전 닉네임을 강제**하기로 했다 (확정 D-5, S-6).

### E. 계정 탈퇴 시 게시글 처리 ✅ 해결

`auth.users` 삭제는 cascade로 전파된다. 커뮤니티 테이블을 그대로 cascade에 물리면 탈퇴 시 글·댓글이 모두 사라진다.

**`on delete set null` + "탈퇴한 사용자" 표시로 확정한다** (D-3).

당초 "cascade가 싸다"고 봤으나 이는 **목표 #2(축적되는 콘텐츠 자산)와 정면으로 충돌**한다. 파워 유저 한 명이 떠날 때 그가 쓴 글 전부가 사라지면 커뮤니티가 쌓아 온 자산이 통째로 증발하고, 남의 스레드에는 구멍이 나며, 진행 중인 신고 증거도 소멸한다. 네이버 카페를 비롯한 국내 서비스 표준도 "탈퇴한 회원" 표기 방식이고, 사실상 익명화이므로 개인정보 관점에서도 올바른 패턴이다. 이용규칙에 해당 조항을 명시한다.

추가 비용은 작다 — 컬럼 nullable화, 표시 폴백 한 줄, 이용규칙 문구.

### F. AppBinding 이중 등록 누락 🔴 (가장 확실하게 터지는 것)

`AppView`의 `IndexedStack`은 5개 탭을 **동시에 build**한다. `/app` 라우트에서는 `AppBinding`만 실행되고 `CommunityBinding`은 **절대 실행되지 않는다.**

`CommunityController`와 Repository 3종을 `AppBinding.dependencies()`에 `Get.lazyPut(..., fenix: true)`로 반드시 등록해야 하며, 빠뜨리면 앱 진입 즉시 `"CommunityPostRepository not found"` 예외가 난다. `CommunityBinding`은 딥링크·푸시로 `/community`에 직접 진입할 때만 쓰인다.

프로젝트 메모리에 이미 기록된 실패 패턴이다 — `.claude/agent-memory/team-lead/bottom_nav_tab_binding_pattern.md`.

### G. 콜드 스타트에 커뮤니티 쿼리가 붙는다 🟡

F와 같은 이유로 `CommunityController.onInit()`에 `fetchPosts()`를 넣으면 앱 시작 때마다 커뮤니티 쿼리가 실행된다.

`PlayerController.reloadFromTab()` 패턴을 참고하되 **동작은 달라야 한다**: `onInit`에서 로드하지 않고 `AppController.changeTab(communityTabIndex)`에서 `_hasLoadedOnce` 플래그로 **최초 1회만** 로드한다. 선수 탭처럼 매번 리셋하면 글을 읽다 다른 탭에 갔다 온 사용자의 스크롤 위치와 목록이 날아간다.

### H. 모델 setter 컨벤션과 GetX 반응성 충돌 🟡

`MODEL_GUIDE.md`는 mutable setter를 관례로 정하고 있지만, 낙관적 좋아요 토글에서 `post.likeCount = n`만 하면 `RxList`가 변경을 감지하지 못한다.

`ChatMessageResponse.copyWithAuthor` 선례를 따라 `copyWithLike`를 만들고 **리스트 요소를 교체**(`_posts[i] = newPost`)한다. 구현 전에 이 방침을 명시적으로 확정한다.

### I. 응답 래퍼 모델을 만들지 않는다 🟢

기존 `get_*_response.dart` 래퍼들은 Edge Function 응답 봉투용이다. 커뮤니티는 `.from()` 직접 접근이라 봉투가 없으므로 `GetCommunityPostsResponse` 같은 걸 만들지 말고, `ChatMessageRepository`처럼 `Future<List<CommunityPostResponse>>`를 반환한다. `hasMore`는 `fetched.length >= pageSize`로 판단한다(`PlayerController`가 이미 쓰는 폴백).

### J. 기타 구현 주의

- **Obx 스코프**: 리스트 4단 분기를 `Obx` 하나로 감싸면 스크롤 중 전체 리빌드가 난다. sliver 단위로 쪼갠다. 신고 시트의 라디오는 `RxString`을 시트 내부에서 읽어야 "improper use of a GetX" 경고를 피한다.
- **스낵바 스팸**: `Get.snackbar`를 남발하면 화면이 덮인다. 기준은 **"사용자가 의도한 액션인가"**다.
  - **로그만** — 조회수 증가처럼 사용자가 요청하지 않은 백그라운드 부수효과, 그리고 목록에서 스크롤 중 우발적으로 눌릴 수 있는 동작 (`PlayerController.loadMore`의 silent 정책)
  - **스낵바** — 작성·수정·삭제·신고·차단, 그리고 **상세 화면의 좋아요 토글**. 하트를 의도적으로 눌렀는데 아무 설명 없이 되돌아가면 원인을 알 수 없다
  - 실패 메시지는 `community_error.dart`의 `communityErrorMessage()`로 변환해 서버 `hint`/`code`에 맞는 한국어를 띄운다
- **차단으로 인한 대댓글 고아**: 부모 댓글 작성자를 차단하면 부모만 사라지고 대댓글이 최상위에 뜬다. 컨트롤러 트리 빌드에서 `parent_id`가 결과 집합에 없는 항목을 드롭한다.
- **댓글 수 불일치**: `comment_count`는 차단을 반영하지 않아 "댓글 5"인데 3개만 보일 수 있다. 업계 표준 동작이며 수정 비용이 크므로 그대로 둔다.
- **EULA 버전 동기화**: 클라이언트 상수와 DB 함수 값이 어긋나면 전 사용자가 글을 못 쓴다. 두 곳을 한 커밋에서 바꾸고 **배포 순서는 DB 먼저**.
- **마이그레이션 후 검증**: Supabase `get_advisors`(security) 실행으로 RLS·GRANT 구멍을 확인한다.
